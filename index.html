Local network audio

Whatever your desktop is playing, on every speaker in the house.

Ausha captures the audio leaving your computer and streams it to laptops and phones on the same WiFi, as Opus over RTP — with the jitter buffer, loss recovery and clock-drift correction that make it hold up on a real network.

Opus 48 kHz stereo 20 ms frames in-band FEC Linux sender Android & desktop receivers

$ cargo run --release --bin ausha
on the listenerreceiver

What it is

One capture, many listeners.

Ausha reads your desktop's loopback device — the same audio your speakers get — encodes it once, and fans the result out to every receiver that has paired with it. Receivers come and go without disturbing the stream, and they all share a single encode.

A datagram is one frame of audio

Each UDP packet carries exactly one 20 ms Opus frame with an RTP header, so a lost packet costs one frame and nothing else. That is what makes the rest of the recovery possible.

Losses get rebuilt, not papered over

Opus carries a low-bitrate copy of the previous frame inside each packet. An isolated loss — the common case on WiFi — is reconstructed from it rather than concealed.

The buffer sizes itself

The jitter buffer grows to absorb whatever bursts your network actually produces, so you are not guessing at a latency setting that will be wrong an hour later.

Clocks drift; this corrects for it

Your phone's converter does not run at exactly the sender's rate. A slow resampler nudges the ratio by fractions of a percent so the buffer neither empties nor grows over hours.

How to use it

Build it, start it, pair a listener.

The sender runs on Linux and needs ffmpeg built with libopus plus a loopback audio device. Receivers need nothing but the binary.

01

Build the workspace

One command builds the sender, the desktop receiver and the shared core.

terminalonce
$ git clone https://github.com/aaxis-em/ausha
$ cd ausha
$ cargo build --release
02

Start the sender

It finds the default sink's monitor source and prints everything a receiver needs to reach it.

desktopausha
$ cargo run --release --bin ausha

capture: pulse source alsa_output.pci-0000_00_1f.3-....monitor
control: tcp/6996
media:   udp/6997 ssrc 1b60ad3b
pairing: xxxx-xxxx-xxxx
The pairing token changes every time the sender starts. Copy the one your own sender just printed, or pin it with --token <token> so you are not retyping it each session.

Find the address listeners should connect to:

desktopaddress
$ ip -4 addr show scope global | grep -oP 'inet \K[\d.]+'
03

Play it on another computer

This is the full pipeline — jitter buffer, FEC, drift correction. The token may be typed with or without dashes, in any case.

listenerausha-recv
$ cargo run --release --bin ausha-recv -- \
    --host <sender-ip> --token <token>

Playback goes to pacat, aplay or ffplay — whichever it finds first. Pick one with --sink, and choose how much the buffer holds with --latency low|balanced|stable.

04

Or pair a phone

The Android app runs the same Rust core. Gradle compiles it for each ABI on the way, so the native library is never stale.

androidgradle
$ cd android
$ ./gradlew installDebug

Then pair it in whichever way suits:

MethodWhat you do
ScanRun ausha --qr and scan the code with the app's Scan QR button.
Tap a linkThe same ausha://host:port?token=… link opens the app directly.
Pick from the listThe app lists senders it finds over mDNS. Tap one and type the token.
Type itAddress, port and token by hand.

Playback keeps going with the screen off, holds a low-latency WiFi lock so the radio does not park between beacons, and pauses for calls.

While it runs

The receiver tells you what it is doing.

Every five seconds, one line. You do not have to guess whether the network is coping.

ausha-recvevery 5 s
    5s  depth  80/ 80 ms  latency  81 ms  jitter   2.5 ms  loss  0.00%
        fec 0  plc 0  underruns 0  rate 1.0000
depth a/b
Undecoded audio buffered, against the target it is aiming for.
latency
Total buffered audio — the delay this receiver adds.
jitter
How irregularly packets are arriving.
loss
Packets that never arrived at all.
fec / plc
Lost frames rebuilt from redundancy, and ones papered over.
underruns
Times the buffer ran dry. Should stay at zero.
rate
Resampling ratio correcting clock drift. Sits near 1.0000.
High loss with underruns still at zero means it is working. The target depth grows on its own to absorb the bursts.

If it does not connect

Two faults look identical from the receiver.

Both show up as a handshake that times out, and neither appears when you test on a single machine.

The firewall is blocking the ports

The sender needs inbound TCP 6996 for the handshake and UDP 6997 for the audio.

sudo ufw allow 6996/tcp && sudo ufw allow 6997/udp

The network isolates its clients

Many routers, and nearly all guest networks, block device-to-device traffic. If the sender answers ping but the handshake still times out, this is why — use a different network.

The token is from an earlier run

rejected: invalid pairing token means exactly that. It changes on every start; use the pairing: line the running sender printed, or pin it with --token.

No senders appear in the app's list

mDNS is blocked on many routers. Scan the QR code or type the address in by hand instead.
